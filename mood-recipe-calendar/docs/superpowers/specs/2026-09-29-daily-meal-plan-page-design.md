# 一日三餐页面设计

## 目标

把一日三餐从最小结果页升级为可在单页完成查看、理解、替换和开始做饭的计划页。只展示服务端校验合格的完整三餐。

## 信息架构

1. 顶部：日期、可选地区、当季提示和刷新入口。
2. 三张菜名卡：早餐、午餐、晚餐。默认只展示餐次、菜名、时长、难度、主要食材和“换一道”。
3. 渐进展开：点击一张卡只展开该卡，其他卡收起；展开内容为封面或锅仔插画、完整食材、步骤和“记录这餐”。
4. 搭配依据：显示食物多样性、蔬菜、蛋白、当季命中和可改善项；附知识包版本与非医疗提示。
5. 购物清单：合并三餐食材，用户可勾选已购买。

## 交互与状态

- 点击菜名卡切换展开状态；不跳转离开当前页。
- “换一道”只调用对应餐次替换 API；卡片显示局部加载，成功后仅更新该卡及搭配依据。
- 图片不存在或加载失败时显示锅仔插画，不能阻塞菜名、食材和做法。
- 有独立的首屏加载、替换加载、无合格结果、网络错误和重试状态；不展示半份菜单。

### 无合格结果状态

- 延续正常结果页的暖杏色背景、圆角 Hero、白色内容卡和珊瑚色主按钮，不使用居中图片加文字链接的孤立布局。
- Hero 左侧依次展示小标题、两行主标题和一句安全说明，右侧使用思考锅仔；装饰图形、阴影、圆角和字号复用现有页面视觉语言。
- Hero 下方使用一张说明卡，列出重新生成会再次核对的三项：忌口安全、当季候选、三餐不重复。文案只描述将执行的检查，不声称失败结果已经通过检查。
- “重新生成”使用项目统一的全宽主按钮；生成期间显示明确文案、禁止重复点击，并保留按压反馈和无障碍标签。
- 页面保留可返回导航，不新增次要功能、弹窗、依赖或独立设计体系。

## 服务端契约

- `GET /api/daily-meal-plan?date=YYYY-MM-DD&region=...` 返回完整三餐、规则版本、搭配依据和购物清单。
- `POST /api/daily-meal-plan/{mealIndex}/replace?date=YYYY-MM-DD` 仅替换对应餐次；替换后必须重新通过整日校验。
- 每个餐次包含菜谱对象、餐次名称、食材与做法；响应不得含乱码或不合格字段。

## 验收

- 默认三张紧凑菜名卡；同一时刻最多展开一张。
- 任意一张可在当前页看到完整食材、做法和记录入口。
- 换一道不改变另两餐，且没有相同菜名或核心食材冲突。
- H5 与小程序均能正常显示无图回退与全部状态。
- 无合格结果页与正常三餐页、首页和记录页属于同一视觉体系；首屏没有无意义的大面积空白或背景断层。
- 连续点击“重新生成”只触发一个加载流程；加载期间按钮展示进行中状态。
