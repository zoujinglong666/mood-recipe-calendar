# 锅仔可视化学习闭环设计

## 目标

把现有的“推荐、做饭、记录、行为学习”能力串成用户能看见、能理解、能控制的闭环：

`推荐 → 跟做 → 上传自己的照片并记录 → 提交轻量反馈 → 锅仔说明学到了什么 → 下次推荐说明因此改变了什么`

首版不建设新的通用事件平台。它复用现有菜谱行为、计划结果、做菜反馈和统一饮食档案，仅增加统一写回服务、学习回执和推荐解释。

## 已确认的产品范围

- 学习回执同时出现在记录成功界面和下一次推荐界面。
- 记录页提供三个可跳过的反馈：`喜欢这道菜`、`做起来太难`、`有剩菜`。
- 记录照片必须由用户自行上传，不从 AI 菜谱图片自动带入。
- 所有解释必须来自实际使用的偏好或反馈；没有依据时不展示，不生成空泛文案。
- 页面风格、按钮、标签、反馈选择器和状态展示必须复用统一组件与设计变量。
- 不新增依赖，不建设独立消息中心，不增加强制问卷。

## 方案选择

采用“复用现有行为数据 + 统一学习回执”方案。

未采用的方案：

- 新建完整事件流水表：追踪能力更强，但对当前闭环明显过度设计。
- 仅前端展示固定文案：实现快，但不能证明下次推荐真的发生了变化。

## 用户流程

### 1. 推荐

推荐结果在菜名与主操作之间展示“锅仔为什么选它”区域。区域最多展示两条：

- `本次参考`：例如“你最近更常选择清淡家常菜”。
- `相比上次`：例如“上次觉得步骤偏难，这次优先选择 25 分钟内的做法”。

只有后端确实使用了对应事实或学习信号时才展示。安全拦截、模型内部提示词和技术降级原因不作为营销文案暴露。

### 2. 跟做

继续使用现有做菜页和分步骤反馈。完成做菜后进入记录页，保留菜名、菜谱关联、心情和烹饪时长，不携带 AI 生成图片。

### 3. 记录与反馈

记录页在心情之后、文字备注之前增加“这次做得怎么样”区域。三个选项均为独立开关，可多选，也可全部跳过：

- 喜欢这道菜：增强相同菜品和相关口味的正向信号。
- 做起来太难：降低复杂做法，并影响做菜教学详细度。
- 有剩菜：后续减少菜量或菜数倾向。

保存记录仍以照片、菜名和心情为必要条件，反馈不是必要条件。

### 4. 学习回执

保存成功后，成功层展示服务端返回的真实学习结果：

- 标题：“锅仔记住这顿了”。
- 记录确认：“照片和心情已收进时光机”。
- 学习条目：最多三条，例如“以后多推荐这类菜”“下次优先更简单的步骤”“下次会控制分量”。
- 主按钮：“看看这顿记录”，进入本次记录详情。
- 次按钮：“返回首页”。

如果学习写回失败但记录保存成功，回执显示“记录已保存，锅仔稍后再整理”，不得要求用户重新上传照片或重复提交。

### 5. 下一次推荐

统一饮食档案将已写回的信号用于候选过滤、排序和推荐解释。推荐响应返回本次实际使用的解释项，前端原样展示，不在客户端猜测原因。

## 后端设计

### 统一写回服务

新增一个聚焦的学习回执服务，接收：

- 用户标识；
- 菜谱 ID 或推荐曝光 ID；
- 菜名；
- `liked`、`tooHard`、`leftover`；
- 记录 ID。

它复用现有能力完成：

- `MADE` 与 `LIKE` 菜谱行为写入；
- 难度与剩菜结果写入；
- `AgentLearningService` 更新统一事实；
- 生成只包含已成功写入结果的回执条目。

记录保存是主事务。学习写回采用记录保存后的受控调用：学习失败不回滚记录，并以降级回执响应。重复的 `clientRequestId` 必须返回同一记录，不能重复增强行为信号。

### 接口变化

记录创建请求增加可选字段：

- `liked: boolean`
- `tooHard: boolean`
- `leftover: boolean`

记录创建响应由单独的记录对象扩展为：

- `record`
- `learningReceipt`

`learningReceipt` 包含：

- `status: LEARNED | SAVED_ONLY`
- `title`
- `items: string[]`

推荐结果增加：

- `recommendationInsights: { type: MEMORY | CHANGE, text: string, memoryKey?: string }[]`

解释由实际排序与档案命中生成，最多两条。

### 数据一致性

- 同一用户、菜谱、行为的重复写入继续使用现有去重规则。
- 曝光菜谱和本地菜谱沿用各自现有反馈入口。
- 关闭个性化后仍保存记录和安全限制，但不写入普通长期偏好；学习回执只确认记录已保存。
- 删除单条记忆或清空记忆后，后续推荐解释不得再引用对应事实。

## 前端设计系统约束

### 统一组件

首版只增加两个共享组件：

- `GuozaiChoiceChips`：用于“喜欢、太难、有剩菜”等多选反馈。统一选中态、禁用态、按压态、字号、圆角和无障碍标签。
- `GuozaiInsightCard`：用于记录后的学习回执和推荐页的推荐解释。统一锅仔图标、标题、条目样式和来源入口；通过 `variant` 区分 `learned` 与 `recommendation`，不复制两套卡片。

现有主按钮继续使用项目统一的主按钮类与颜色变量。成功层的主次按钮复用同一尺寸、圆角、按压反馈和加载规则，不在页面内重新定义按钮视觉。

### 视觉规则

- 使用现有暖白、珊瑚橙、深棕文字和锅仔 IP 素材。
- 卡片圆角、边框、阴影、间距全部引用现有 `--mrc-*` 变量。
- 同一语义只有一种样式：主操作、次操作、危险操作、选择标签、信息卡分别保持一致。
- 不增加渐变种类、玻璃拟态、独立图标库或页面专属颜色。
- 动效仅使用现有按压缩放和淡入；尊重 `prefers-reduced-motion`。

## 错误与降级

- 记录保存失败：停留当前页并保留全部照片、表单和反馈选择。
- 记录成功、学习失败：显示 `SAVED_ONLY`，允许正常查看记录。
- 推荐解释为空：不渲染解释卡，不显示占位文案。
- 推荐解释包含已删除或已禁用的普通记忆：后端过滤，前端不承担二次判断。
- 用户重复点击保存：沿用提交锁与 `clientRequestId` 幂等保护。

## 测试与验收

### 后端

- 保存带反馈的记录后，返回记录和学习回执。
- 喜欢、太难、剩菜分别写入正确的既有行为或计划结果。
- 重复 `clientRequestId` 不重复学习。
- 学习失败不影响记录保存。
- 关闭个性化后不写普通偏好，但安全限制继续生效。
- 下一次推荐只返回实际使用的解释。
- 删除或清空记忆后，推荐解释不再引用它。

### 前端

- 三个反馈可多选、取消和全部跳过。
- 提交中不可重复保存，失败后选择不丢失。
- 成功层展示服务端回执并能打开本次记录。
- 推荐解释为空时不留空白区域。
- 两个页面复用同一信息卡组件；所有反馈入口复用同一选择组件。
- 相关文件通过 ESLint、类型检查和小程序构建；已有第三方依赖错误需与新增错误分开记录。

## 完成标准

一次真实操作能够证明完整链路：用户从推荐进入做菜，上传自己的照片，选择反馈并保存；成功层准确说明锅仔学到的内容；下一次推荐结果发生相应排序变化，并展示来自同一事实的解释。整个过程不要求重复输入，也不会展示未经实际写入的学习结论。
