## Context

项目已有过敏归一化、用户饮食偏好、首页单菜推荐、周菜单与锅仔智能体。它们尚未形成“地区季节性 + 全天三餐搭配 + 可解释规则”的统一决策链。参见 `proposal.md` 中关于未授权指南文本和图示不得进入产品的约束。

## Goals / Non-Goals

**Goals:**

- 使用独立、版本化的当季食材目录与知识包（KPK）生成日计划。
- 采用 `nutrition-skill-methodology` 的框架、知识包结构和质量校验流程；在产品的第三方声明中保留其作者署名和 MIT 许可证文本。
- 让过敏和忌口在模型调用前后都作为不可绕过的限制。
- 将一日三餐的生成、替换与解释设计为可测试的确定性流程，模型仅在菜谱表达和候选排序中辅助。

**Non-Goals:**

- 不接入未授权 PDF 的 RAG、向量库、全文搜索或官方图示。
- 不将 `nutrition-skill-methodology` 或其他开源仓库引用的第三方指南原文视为已获授权内容。
- 不估算治疗所需能量、提供疾病食谱或替代医生、营养师建议。
- 第一期不处理儿童、孕产妇、老年人和慢病等专属人群规则。

## Decisions

### 规则先于模型，解释独立于模型

菜单先经过过敏、忌口、当季、重复食材、预算和烹饪时间的确定性筛选；模型只能从已合格候选中组合或润色。解释由规则命中记录生成，避免模型把一般建议说成医疗结论。

备选方案是用 RAG 提示词让模型自行决定。该方案无法保证安全限制和结果可复现，且在无授权时不能使用目标 PDF，故不采用。

### 以 KPK 知识包承载规则与溯源

每条可执行规则以一个版本化知识包保存，字段至少包括：`id`、`version`、`title`、`audience`、`recommendation`、`ingredientNotes`、`hardConstraints`、`explanation`、`sourceKind`、`sourceReference`、`licenseStatus`、`reviewedAt` 和 `enabled`。规划服务只加载 `enabled` 且 `licenseStatus=commercially-usable` 的知识包；`sourceReference` 必须能够定位到自有内容或授权凭据。该结构参考 `nutrition-skill-methodology` 的 KPK 和框架工作流，但知识包中的实际规则文本由产品独立撰写或来自已获明确商用授权的来源。

备选方案是将长篇指南全文放进向量库并让模型引用。该方案既无法证明每段材料的内容权利，也不利于逐条测试硬限制，故不采用。

### 四层质量校验

规划请求必须依次通过：输入校验（日期、健康成人范围和偏好格式）、候选校验（季节、过敏、忌口及许可证）、模型输出校验（结构、菜名、食材与跨餐去重）和展示前校验（完整性、可读 UTF-8 文本、知识包版本与非医疗提示）。任意一层失败时，不展示部分结果；服务可改用合格候选重试一次，仍失败则返回可恢复的“暂时无法生成合格菜单”状态。

### 以“食材快照 + 规则版本”保存日计划

每次保存日计划时记录食材季节数据、搭配规则版本与命中理由。后续维护当季目录不会重写用户历史菜单，也能解释当时为什么这样推荐。

### 地区采用渐进粒度

第一期用大区与全国通用季节数据，不要求用户提供精确地址；前端将地区设为可选项。后续根据数据质量再扩展至省市，不在第一期承诺精确到城市。

## Risks / Trade-offs

- [当季食材受气候、物流与市场供应影响] → 仅描述“优先当季候选”，保留替代食材和用户换一道入口。
- [用户误把日常建议理解为医疗建议] → 固定显示非医疗提示；特殊健康目标不进入第一期自动规划。
- [模型输出绕过限制] → 结果在模型输出后再次运行过敏、忌口与去重校验；不合格则拒绝展示并重新选择候选。
- [开源方法论与其引用来源的授权被混淆] → 每条知识包独立记录内容来源与商用许可状态，方法论的 MIT 许可不作为第三方资料的授权凭据。
- [模型返回乱码或缺字段] → 展示前进行 UTF-8、字段完整性、标题可读性和跨餐重复校验；不合格结果不写入历史菜单。
- [规则过多导致体验像填表] → 规划入口只要求日期，地区、预算、库存和时间为渐进补充项。

## Migration Plan

1. 先建立带来源和许可状态的知识包、无版权争议的当季食材与原创规则种子数据，并覆盖测试用地区和月份。
2. 新增日计划领域模型与生成接口，复用既有偏好、过敏和菜谱数据。
3. 接入前端的“一日三餐”入口、替换和解释页面；保持原首页推荐、周菜单入口不变。
4. 灰度开放给健康成人用户，收集替换率、采纳率和禁忌拦截日志。
5. 取得明确授权后，以独立变更新增 RAG 证据层，不改写本变更的硬规则。
