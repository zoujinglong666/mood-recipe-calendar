## Context

今日推荐页已有原生分享按钮，但未生成内容卡。画册已有一套 Canvas 2D 导出与保存逻辑，可作为跨端实现的既有模式；本次不需要后端数据或新依赖。

## Goals / Non-Goals

**Goals:**

- 让一条当前推荐一次生成、一次保存，并保持菜品成为视觉主角、锅仔负责解释推荐的现有页面叙事。
- 兼容微信小程序与 H5，且为资源、权限和导出失败提供恢复路径。

**Non-Goals:**

- 不创建公开的菜谱详情、二维码、分享统计或图像云端存储。
- 不让 Canvas 卡片成为新的数据来源；它只消费当前页面已有的推荐数据。

## Decisions

### 复用 Canvas 2D 导出模式

新增一个轻量食谱卡导出工具，采用画册现有的 `type="2d"` Canvas、节点查询、图片加载与 `canvasToTempFilePath` 模式。它不依赖 DOM 截图或浏览器专有 API，因此微信小程序能直接生成高分辨率 PNG。

备选方案是截取页面或引入海报库；前者无法稳定跨端，后者会增加包体与依赖，均不适合当前需求。

### 卡片以当前推荐为唯一输入

导出数据只使用页面已有的菜名、心情、菜图、锅仔推荐理由、制作时长、食材摘要和静态锅仔资源。菜图或锅仔资源使用失败时跳过绘制对应图片，保留带色块和文字的可读版式；不将用户偏好、历史做菜记录或 AI 推理写入卡片。

### 生成与保存分为一个连续操作

分享入口提供“生成并保存食谱卡”和“分享菜谱链接”两个明确动作。生成期间禁用重复触发并显示进度；小程序使用相册保存，H5 在条件编译分支中以下载方式处理 PNG。普通分享始终独立可用，不依赖卡片生成成功。

### 原生分享只传可恢复的路由状态

通过 `onShareAppMessage` 和当前路由的心情参数构造标题与路径。菜谱正文不塞进 URL；接收者进入后按已有推荐流程获取内容，避免披露私人数据或依赖临时图片地址。

## Risks / Trade-offs

- [远程菜图未配置下载域名或跨域] → 跳过菜图绘制，导出文字卡并在界面说明可继续保存。
- [用户未授予相册权限] → 显示授权失败信息，保留再次保存入口，不阻断原生分享。
- [H5 浏览器阻止自动下载] → 仅在用户点击动作内触发下载；失败时保留可预览的临时图与提示。
- [Canvas 字体和长文本截断] → 限定卡片字段与行数，按字符裁剪并使用固定字号，不渲染完整食材正文。

## Migration Plan

1. 先上线卡片生成与保存，保留当前分享按钮的原生菜单能力。
2. 在微信开发者工具与 H5 分别验证图片、无图片、拒绝权限和导出失败路径。
3. 若导出工具出现平台兼容问题，回退为仅保留现有原生分享入口；不涉及数据迁移或服务端回滚。

## Compatibility and Verification

- 代码影响限于今日推荐页与一个前端导出工具；不改变接口、数据库或虚拟支付。
- 验证 Canvas 绘制数据、无菜图降级、微信保存调用、H5 下载分支、分享标题与路径，以及前端类型检查。
