## Context

现有 `src/utils/albumShare.ts` 通过 Canvas 2D 生成两种食谱卡。两种卡片共用大面积圆角卡片和固定坐标，推荐理由区的图标与长文本容易挤压。导出入口已被食谱页和周菜单详情页复用，因此设计必须维持 `exportRecipeShare` 的调用方式和跨端保存逻辑。

## Goals / Non-Goals

**Goals:**

- 为两种风格建立共同的暖白、深棕、番茄红设计令牌与固定的竖向网格。
- 让顶部主视觉、内容正文和二维码页脚各自拥有不可重叠的边界。
- 使用户提供的小程序码随前端包发布，离线于 Canvas 读取。

**Non-Goals:**

- 不生成动态或按菜谱变化的小程序码。
- 不改变海报尺寸、食谱字段、页面交互和保存 API。
- 不新增字体、第三方二维码库或服务端接口。

## Decisions

### 共享编辑页式正文与区分顶部主视觉

三种风格共用一套从顶部主视觉、正文网格到二维码页脚的纵向节奏；经典版采用整幅菜图与深色信息带，锅仔版采用菜图拍立得与锅仔插画，手写版采用带横线的便签纸、轻微倾斜的拍立得菜图和红色批注线。这样既保留用户已有的风格选择，又避免三份完全独立坐标布局长期失控。

备选方案是完全统一为一种海报。该方案更易维护，但会移除已有的“锅仔陪伴”与“锅仔手写”表达，因此不采用。

### 以细分隔线替代连续白色大卡

推荐理由采用带侧边标记的编辑注记，食材使用两列网格，做法使用紧凑编号列表；只让顶部视觉使用大圆角。这样降低圆角容器的重复感，并给正文留出更稳定的基线和留白。

备选方案是保留三张白卡并调整间距。该方案不能解决层级同质化与文字碰撞，故不采用。

### 打包静态小程序码并固定在页脚

小程序码放入 `src/static`，由分享函数以本地资源路径载入。二维码画在白色方形静区中，并与短说明共同位于底部固定区域；正文最大行数按页脚起始坐标约束。

备选方案是使用远程 COS URL。它会让离线或网络失败时二维码缺失，也增加图片加载时序风险，故不采用。

### 用笔记元素模拟手写，而非依赖系统手写字体

手写版使用轻微旋转、较紧的标题字距、横线纸张与红色批注线建立手写感觉，正文仍使用跨端稳定的无衬线字形。微信小程序与 H5 对系统字体支持不一致，且动态菜名不能依赖静态字图，因此不加载系统手写字体或逐字图片。

## Risks / Trade-offs

- [小程序 Canvas 无法读取远程或无效图片] → 二维码使用打包的本地 JPG，加载失败时保留白色二维码框与文字，不阻断海报导出。
- [图片或文本过长] → 对所有可变文本使用已有的截断换行函数和固定最大行数，正文坐标不随内容无限增长。
- [二维码被过度缩小导致识别失败] → 以不小于 116 逻辑像素的正方形绘制并保留白边，不在其上覆盖半透明效果。

## Migration Plan

1. 将用户提供的小程序码加入前端静态资源并在分享导出中引用。
2. 替换食谱海报的 Canvas 版式；维持既有函数参数和导出尺寸。
3. 在食谱页生成三种风格，在周菜单详情页生成锅仔风格，验证生成与保存。
4. 若出现特定端的 Canvas 图像加载问题，回退到不含二维码图片但保留扫码占位与正文版式的海报，不影响保存。
