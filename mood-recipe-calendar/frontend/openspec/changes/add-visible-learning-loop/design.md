## Context

参见 `proposal.md` 的 Why。当前推荐、跟做、记录、菜谱行为和统一记忆已经存在，但写回分散，记录接口只返回记录本身，菜谱响应也没有结构化的推荐解释。现有前端页面各自定义局部按钮和卡片样式，新增闭环必须避免继续复制。

## Goals / Non-Goals

**Goals:**

- 使用现有行为、曝光和统一记忆数据形成可验证的学习闭环。
- 记录优先，学习逐项降级，并向用户返回实际成功结果。
- 让难度与分量反馈真正改变后续推荐，而不只是展示文案。
- 通过两个共享组件统一反馈选择、洞察卡和相关按钮状态。

**Non-Goals:**

- 不建设通用事件流水、消息中心或新的数据库表。
- 不为旧记录补算学习回执，不把解释文案持久化。
- 不展示模型提示词、安全过滤细节或无法证实的推断。

## Decisions

### 复用既有事实层，不新增学习事件表

新建聚焦的记录学习服务，复用菜谱行为、推荐曝光和统一记忆。喜欢写入既有行为；太难写入简单做法与时长限制；剩菜写入减少剩余倾向。替代方案是新增通用事件表，但当前没有跨产品分析需求，成本高于收益。

### 记录先保存，学习结果逐项收集

记录仍由现有幂等请求标识保护。只有首次保存后才执行学习；每个学习信号独立捕获失败，回执只包含成功项。重复请求返回既有记录且不再次学习。这样学习服务不可用时不会丢失用户照片和记录。

### 推荐解释是响应瞬态数据

菜谱增加不入库的结构化解释列表，最终菜谱选定后再根据本次确实读取的统一档案生成，最多两条。删除、清空或关闭个性化会让档案不再返回普通事实，因此后续解释自然消失。替代方案是持久化展示文案，但会造成删除记忆后仍显示过期解释。

### 学习结果必须参与排序或约束

统一记忆快照补充简单做法、时长上限和喜欢菜品。AI 推荐提示读取这些字段；本地回退排序对满足时长和简单做法的菜加分，对超限菜扣分。解释服务只能引用这些实际参与本次选择的字段。

### 前端只增加两个共享组件

`GuozaiChoiceChips` 负责多选反馈的正常、选中、禁用、按压和无障碍状态；`GuozaiInsightCard` 负责学习回执和推荐解释，通过语义变体改变标题与锅仔图片，不复制布局。成功层复用同一主次按钮结构和现有 `--mrc-*` 设计变量。

## Code Impact

- 后端修改记录请求/响应、记录控制器、菜谱瞬态响应、统一记忆快照和单菜推荐服务；新增记录学习与推荐解释服务及其测试。
- 前端修改记录/菜谱 API、记录页、推荐页和成功层；新增两个 `src/components/guozai` 共享组件。
- 不修改数据库结构，不引入新依赖，不手工维护页面生成文件。

## Compatibility

- 三个反馈字段均可选，旧客户端请求继续有效。
- 新建记录响应从记录对象变为组合对象，需要前后端同批发布；编辑、查询和删除接口保持不变。
- H5 和微信小程序共享 Vue 组件与接口；图片选择仍使用项目已有跨端封装，不使用浏览器专属 API。

## Risks / Trade-offs

- [一次明确的“太难”可能过度影响推荐] → 只应用确定的简单做法与时长上限，并允许用户在锅仔记忆页删除。
- [学习部分成功导致回执不完整] → 每条回执只对应已成功写入项；全部失败时返回保存成功降级状态。
- [推荐解释与实际排序脱节] → 只在最终选菜后从本次参与选择的档案字段生成，不允许前端推断。
- [旧客户端不认识组合响应] → 前后端同批发布；服务端保留所有旧请求字段兼容性。

## Migration Plan

1. 先部署兼容旧请求的后端请求字段、学习服务和组合响应。
2. 同批发布读取组合响应的新前端，并验证 H5 与微信小程序构建。
3. 观察记录保存错误率与学习降级比例；异常时可回滚前端，后端旧请求仍可保存记录。
4. 无数据库迁移；回滚不需要数据修复。

## Verification

- JUnit/Mockito 覆盖学习成功、部分失败、重复请求、关闭个性化、推荐变化与解释过滤。
- 前端相关文件执行 ESLint、TypeScript 检查和微信小程序构建。
- OpenSpec 严格校验、`git diff --check` 和真实流程人工验收共同作为完成门槛。
