## Context

参见 `proposal.md` 的 Why。当前系统字体在 `App.vue` 和 `.mrc-page` 重复硬编码，未显式覆盖所有页面容器与表单控件；部分业务样式还使用 `850/900` 字重。uni-app 同时输出 H5 与微信小程序，因此方案必须只依赖两端共同支持的 CSS 与系统字体。

## Goals / Non-Goals

**Goals:**

- 用公共主题变量作为字体家族与字重的唯一来源。
- 保持页面现有字号和视觉层级，最小化回归范围。
- 不增加字体下载、依赖和运行时逻辑。

**Non-Goals:**

- 不建立完整排版组件库，也不机械统一所有字号与行高。
- 不修改第三方组件源码和富文本渲染器的等宽字体语义。

## Decisions

### 1. 使用系统字体栈而非网络字体

公共主题定义系统字体栈，页面根节点和常用容器统一继承，表单控件显式继承。相比内置或远程字体，这一方案没有包体、授权、闪烁和离线风险，并符合当前产品的中文阅读场景。

### 2. 字重收敛到标准阶梯

保留 `400/500/600/700/800` 阶梯，将现有 `850/900` 收敛到 `800`。这保留重标题的视觉强调，同时避免不同字体引擎对不存在字重进行不可预测合成。

### 3. 只处理字体基础，不重排字号

现有字号承担各页面具体信息层级，整库改写会扩大视觉回归。本次只统一字体入口与异常字重；后续若需要系统化字号，应基于真实页面验证另立变更。

## Risks / Trade-offs

- [不同操作系统的系统中文字体字形仍略有差异] → 使用相同优先级和标准字重，保证度量与层级尽可能稳定。
- [第三方组件可能保留自己的字体声明] → 不修改第三方源码；业务根节点和常用原生控件保持统一，降低升级冲突。
- [900 改为 800 后个别大标题略轻] → 保留字号、颜色与间距，视觉强调仍成立，并通过页面构建与目测核对。

## Migration Plan

1. 在公共主题加入字体家族与字重令牌。
2. 将应用根节点和页面容器改为消费令牌，令表单控件继承字体。
3. 将业务源码中的 `850/900` 改为 `800`。
4. 执行源码扫描、lint、类型检查和 H5/微信小程序构建。

回滚时恢复公共字体声明和原字重即可；无数据与 API 迁移。

## Verification

- 扫描业务源码，确认不存在 `font-weight: 850/900` 和重复硬编码业务字体栈。
- 执行改动文件 lint、TypeScript/Vue 静态检查、H5 与微信小程序构建。
- 目测推荐页、设置页和“我的”页的标题、正文、标签、输入框在浅色/深色下层级稳定。
