## Context

参见 `proposal.md` 的动机以及 `specs/rag-cooking-coach/spec.md` 的行为约束。现有做菜页已具备菜谱草稿、分步计时、进度恢复和完成记录；后端已有统一大模型客户端、用户记忆、菜谱安全和微信内容安全能力，但没有烹饪知识检索、基于当前步骤的对话编排和可追溯来源。

## Goals / Non-Goals

**Goals:**

- 在现有做菜页内增加可降级的教学生成与连续问答，不重做计时和进度逻辑。
- 用最小数据结构保存经过审核的烹饪知识及来源，支持可验证检索。
- 让模型输出结构化教学和回答，服务端验证后再返回前端。
- 将学习限定为可查看、可关闭、可清除的熟练度证据。

**Non-Goals:**

- 第一版不训练或微调模型，不引入向量数据库、语音识别或图片熟度识别。
- 不让模型自动修改原始菜谱，也不把完整对话或模型推理过程写入长期记忆。
- 不提供医疗营养诊断或代替食品安全专业判断。

## Decisions

### 1. 先用 MySQL 知识块和轻量相关性排序

新增知识块数据，保存标题、正文、分类、关键词、适用食材或技法、来源名称、来源地址、版本、审核时间和启用状态。检索先使用规范化关键词命中、分类与当前菜谱标签加权，返回少量最高分结果。

选择理由：首版知识量可控，MySQL 已存在，避免引入新的运行时和运维面；来源审核比相似度算法更影响答案可靠性。替代方案是立即接入 embedding 与向量库，但在缺少评测集和规模证据时成本更高且难以判断收益。检索代码保持集中，达到数据规模或命中率阈值后再替换内部算法，不预建只有一个实现的接口层。

### 2. 使用一个做菜智能体回合接口

服务端提供单一回合入口，接收菜谱标识、当前步骤、本次会话标识、用户消息以及可选动作（生成指南或提问）。服务端加载可信菜谱、按开关读取最小用户记忆、检索知识、调用现有大模型客户端、校验结构和安全规则，返回：可展示回复、结构化教学步骤、实际来源、使用的记忆类型、降级状态和建议快捷问题。

选择理由：生成指南和现场问答共享同一上下文与校验路径，一个入口能避免两套编排逐渐不一致。前端仍根据返回内容渲染指南或聊天气泡。替代方案是多个细粒度接口，但首版会重复鉴权、检索和降级逻辑。

### 3. 模型只组织答案，事实来自菜谱与知识库

提示上下文只包含当前任务必要的菜谱、步骤、用户选择性记忆和命中知识。模型必须返回既定 JSON 结构；服务端丢弃未知字段、校验步骤数量和必填信息，并把来源列表从服务端检索结果组装，不能接受模型自报来源。高风险食材和过敏信息经过现有安全规则再次检查。

选择理由：这样能防止伪造引用并保持前端数据稳定。替代方案是直接展示模型自由文本，开发更快但无法可靠验证来源、步骤和降级状态。

### 4. 学习采用事件证据，不维护神秘的总评分

仅记录菜谱、步骤类型、结果、难度反馈、重复求助次数和时间。请求时从近期事件推导 `BEGINNER`、`GUIDED` 或 `COMPACT` 教学密度；单次失败不降低等级。用户关闭个性化时不读取事件，清除操作删除其学习事件。

选择理由：事件可以解释、纠错和删除，避免一个不可追溯的数值控制用户体验。替代方案是持续更新单一熟练度分数，但难以解释且容易被偶发反馈污染。

### 5. 前端渐进增强现有做菜页

保留现有完整做法、计时器、材料和完成流程。进入页面后异步请求教学增强，先展示已有步骤；成功后在当前步骤补充“火候 / 看什么 / 失败补救”，底部固定聊天输入与快捷问题，来源使用可展开区域。所有异步状态使用现有跨端组件和 `uni` 能力，不依赖浏览器专属 API。

选择理由：即使服务不可用仍能做菜，也避免引入第二个页面和两套进度状态。替代方案是独立智能体页，但会造成上下文跳转和状态同步问题。

### 6. 降级结果是一等返回值

检索无命中时允许模型基于原始菜谱给出保守一般建议，但来源为空并标记 `NO_EVIDENCE`；模型超时或结构不合格时返回原始步骤与固定安全提示并标记具体降级原因。只对结构错误或瞬时失败进行一次受控重试。

选择理由：明确降级比静默编造更可信，一次重试可控制等待时间和成本。前端始终展示当前状态，不把占位答案伪装成完整智能体结果。

## Data and API Shape

- `cooking_knowledge_chunks`：知识正文、标签、来源、版本、审核与启用状态。
- `cooking_learning_events`：用户、菜谱、步骤类型、反馈类型、时间；不保存模型推理过程。
- 做菜智能体回合响应包含 `reply`、`guideSteps`、`sources`、`memoryUsed`、`suggestions`、`degraded` 和 `degradeReason`。
- 会话只用于本次连续问答；长期学习必须通过明确的结果或难度反馈写入。

## Risks / Trade-offs

- [关键词检索对口语或同义词召回有限] → 首批知识维护同义关键词并记录无命中问题；有真实评测数据后再引入 embedding。
- [模型可能输出无法执行或危险步骤] → 结构校验、菜谱约束、食品安全规则和保守降级共同拦截；来源由服务端组装。
- [生成等待影响做菜节奏] → 原始步骤立即可用，教学异步增强；限制上下文和检索条数，并缓存同菜谱同教学密度的指南。
- [个性化让用户感到被监控] → 默认只使用明确反馈，展示使用的记忆类型，提供关闭与清除入口。
- [知识内容过期或质量不一] → 只检索启用且已审核条目，响应显示更新时间，支持停用与版本更新。

## Migration Plan

1. 新增知识块和学习事件表；先导入一组有来源、已审核的高频技法与食品安全知识。
2. 部署后端检索、智能体回合和降级逻辑，默认不改变现有做菜页行为。
3. 前端以渐进增强方式接入，并通过功能开关小范围启用，观察成功率、无命中率、响应时间和降级原因。
4. 验收后扩大启用范围；回滚时关闭功能开关，保留原始做菜流程，新增表不影响现有数据。

## Compatibility and Verification

- 数据库变更只新增表，不修改现有菜谱与记录结构。
- API 只新增入口；现有做菜草稿、计时、记录和分享接口保持兼容。
- 后端验证覆盖真实来源、不伪造引用、个性化开关、安全规则、一次重试与各降级路径。
- 前端验证覆盖 H5 与微信小程序的加载、成功、无命中、失败、重试、键盘遮挡和原有进度恢复。
