## Context

现有系统具有锅仔偏好、AI 菜谱生成、菜谱库和记录时光机，但这些能力均围绕单次推荐。周计划需要将 AI 输出转为可保存、可替换和可合并的数据，而非把一段自由文本直接展示给用户。

## Goals / Non-Goals

**Goals:**

- 建立最少的计划数据模型，支持一周晚餐、购物项和购买状态。
- 强制 AI 使用结构化 JSON 输出，并在保存前完成字段、天数、步骤数和忌口校验。
- 用现有菜谱与锅仔记忆提供回退或约束，不增加新的外部服务。

**Non-Goals:**

- 不承诺真实价格、热量、减重效果或食材库存准确性。
- 不做自动续订、配送或多家庭协作。

## Decisions

- 数据拆为 `weekly_meal_plans`、`weekly_meal_days`、`weekly_shopping_items` 三张表。计划日保存结构化菜式与食材 JSON；购物项保存规范化名称、数量文本、分类和 `purchased`，避免前端重新解析 AI 文本。
- 生成接口先读取服务器侧用户身份与锅仔记忆，并将人数、预算、厨艺、计划约束放入 JSON-only 提示词。后端解析后校验：日期数、每日菜式、步骤最多五步、禁忌词；不合格则拒绝保存并让用户重试。
- 单日替换请求只生成该日，随后由后端基于全部计划日重新合并购物项。以规范化食材名映射旧购物项，保留仍存在项的 `purchased` 状态。
- 预算作为提示词的预算区间和菜式复杂度约束，而非货币总价计算；页面固定说明实际菜价随地区与季节变化。
- 前端采用两页：计划器收集少量条件（包括每天菜品数）并展示生成进度；计划详情以一周七张可左右滑动的按天食谱卡为主，每张卡展示当天菜品组合，周几标签同时提供可点击的切换入口，食材与做法按需展开，购物清单独立折叠。入口置于“我的”页，与锅仔记忆、时光机共同构成长期陪伴与规划区域，不影响“今日推荐”首屏。
- 每次生成创建一份新的周计划而非覆盖旧计划；入口页面同时呈现当前计划、重新生成入口和最近历史。历史计划可单独打开、收藏，仍可用于查看做法、采购和记录，不会默认为当前计划。
- 每个计划日保存可选 `imageUrl`。详情页进入或切换到某日时请求该日封面；后端复用 `AgnesRecipeImageService` 生成后写回计划 JSON。无密钥、超时或供应商失败时保留菜谱正文并使用已有菜谱图或无图状态，绝不把图片失败变成计划生成失败。
- 订阅消息仅在“生成新的这一周”这个用户点击动作中由小程序调用 `requestSubscribeMessage`；授权结果随生成请求提交。后端在计划成功保存后复用 AppID/Secret 获取并缓存 access token，发送模板 `time3`（完成时间）与 `thing4`（提醒），跳转到计划详情。授权被拒、令牌或发送失败只记录最少错误码，不影响主流程。
- 周计划的 Agent 采用“规划—选菜—校验”闭环：锅仔先读取用户偏好、忌口、菜系、健康目标、近期拒绝与已做记录；再按每日菜数选择主菜与配菜并降低重复；最后由计划服务校验每天数量并据全部菜品合并采购清单。此逻辑在本地菜谱库完成，不依赖模型可用性；后续可在不改变数据契约的前提下替换为结构化模型规划。

## Risks / Trade-offs

- [AI 返回不稳定] → 严格 JSON 解析与校验失败即重试，不用不完整文本兜底。
- [食材同义词无法完全合并] → 首版维护基础规范化词典，无法识别时保留独立项；后续由真实数据补充。
- [生成耗时长] → 复用现有推荐任务式进度展示，明确“正在安排菜单 / 合并食材 / 整理清单”。
- [计划变得过于复杂] → 首版限定晚餐和 7 天以内，入口默认 7 天；用户可选每天 1–3 道菜，三人默认两道，并优先组合一荤一素或一锅出。

## Migration Plan

1. 创建计划、计划日和购物项表，均关联当前登录用户。
2. 部署后不影响既有菜谱、偏好和记录数据；新入口独立上线。
3. 出现生成故障时可隐藏入口或返回生成页重试，不影响原有单次推荐。
