## Context

现有锅仔记忆使用一个用户偏好实体和 `GET/PUT/DELETE /api/preferences` 管理口味标签、具体菜名、葱香菜、辣度、忌口及过敏；心情推荐、AI 深度推荐和锅仔寄语已经读取该实体。菜谱目录没有独立菜系字段，因此本变更需在不重构菜谱表和推荐架构的前提下加入可用的菜系偏好。动机见 `proposal.md`，行为约束见 `specs/favorite-cuisine-memory/spec.md`。

## Goals / Non-Goals

**Goals:**

- 复用现有偏好读取、保存、清除和登录流程，以最少字段贯通前后端。
- 让菜系偏好真实影响推荐评分、推荐理由、AI 上下文和锅仔寄语，而不是只停留在表单展示。
- 对既有数据、空值、H5 和微信小程序保持向后兼容。

**Non-Goals:**

- 不新增菜系管理后台、菜谱分类表或机器学习模型。
- 不根据用户历史行为自动写入菜系偏好；只有用户主动确认的选择才进入长期记忆。
- 不让菜系权重覆盖忌口、过敏、拒绝记录与近期去重等安全和体验规则。

## Decisions

### Decision: 在现有偏好实体增加逗号分隔的 `favoriteCuisines`

使用与 `favoriteTags` 相同的存储与 API 形态，默认空字符串、最长 500 字。这样数据库可通过现有 JPA schema 更新策略向后兼容扩列，前端也可复用数组与字符串互转逻辑。

替代方案是建立用户与菜系多对多关系表；当前菜系数量固定且只需整体读写，多表会增加仓储、事务和迁移复杂度，暂不采用。

### Decision: 使用小型菜系关键词字典为现有菜谱评分

推荐层把用户选择的菜系映射为一组代表菜名或风味关键词，在现有 `preferenceScore` 与推荐理由判断中复用。菜系命中只增加有限权重，候选过滤顺序保持不变。

替代方案是在每道菜上新增菜系字段并重写全部种子数据；在菜谱目录仍较小且许多家常菜跨菜系的当前阶段，维护成本高于收益。未来菜谱进入运营后台并具备结构化分类时再升级。

### Decision: AI 与寄语直接读取用户确认的原始菜系名称

AI 深度推荐把菜系作为长期偏好文本的一部分；锅仔寄语将首个菜系作为可选个性化变量，并在提示上下文中包含完整选择。这样无需新增生成接口或缓存层，保存偏好后沿用现有缓存失效逻辑即可看到变化。

### Decision: 在现有锅仔记忆页加入独立多选区

使用现有 `choice-grid` 和 `choice-chip`，把菜系区放在口味标签之后、具体菜名之前。已选状态同时通过颜色和选择状态表达，触控尺寸沿用现有跨端标准，不引入 Wot UI 新组件。

## Risks / Trade-offs

- [关键词字典只能覆盖当前常见菜谱，无法精确表达融合菜或地域细分] → 命中只做加权而不做硬过滤；目录结构化后可平滑迁移为菜谱字段。
- [逗号分隔值不适合复杂查询] → 当前仅按单用户整行读取并在内存评分，数据规模和访问方式可控。
- [菜系选择过多会削弱个性化] → 前端提供有限、易懂的常见选项，但暂不强制数量上限，避免引入额外校验分支。
- [自动建表策略在正式环境可能关闭] → 上线前通过现有数据库迁移方式增加可空字段；回滚时旧版本会忽略新增列，无需删除数据。

## Migration Plan

1. 在用户偏好表增加可空或默认空字符串的菜系字段，先部署兼容新旧请求的后端。
2. 部署包含菜系选择的 H5 与微信小程序前端。
3. 验证旧用户读取为空、新用户保存回读、清除记忆、推荐命中和无命中回退。
4. 如需回滚，仅回滚前后端代码；保留新增列不会影响旧版本。
