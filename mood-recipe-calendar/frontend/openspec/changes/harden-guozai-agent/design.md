## Context

参见 `proposal.md`。当前后端以 `GuozaiAgent` 编排记忆、文本模型、图像模型和本地降级；本地菜谱依靠数据库 ID 记录互动，而 AI 菜谱是无 ID 的临时对象。推荐进度通过轮询读取，文本模型调用是同步非流式请求。

## Goals / Non-Goals

**Goals:**

- 在现有 Spring/JPA 与 uni-app 请求层内修复安全和一致性问题。
- 保持本地菜谱 ID 反馈兼容，并让 AI 推荐获得可反馈的稳定身份。
- 用少量确定性代码守住过敏、忌口和付费权益边界。
- 保持 H5 与微信小程序行为一致。

**Non-Goals:**

- 不增加通用 Agent 框架、工具调用循环或新的第三方依赖。
- 不实现供应商流式协议，不展示模型内部推理。
- 不保存完整 AI 菜谱正文，不改推荐页面布局。

## Decisions

### Decision: 使用轻量推荐曝光记录而不是持久化完整 AI 菜谱

曝光记录保存随机 UUID、用户、菜名规范化指纹、来源、动作与时间。推荐响应增加可选 `exposureId`；本地菜谱继续使用原有 `id`。这样能完成反馈和去重，同时避免长期保存完整菜谱与用户画像。

替代方案是直接把生成菜谱写入 `recipes`，但这会污染公共菜谱库，并扩大内容审核和存储范围，因此不采用。

### Decision: 饮食限制由统一确定性校验器负责

普通推荐、深度推荐和本地降级共享相同的菜名与配料文本检查。提示词仍用于指导模型，但不被视为安全边界。AI 结果不合格时普通推荐回退本地库；深度推荐返回失败并恢复权益。

替代方案是让模型自检或二次调用模型，无法提供确定性保证且增加成本，因此不采用。

### Decision: 权益消费使用控制器内单次补偿保护

请求先验证，再消费权益；消费成功后用单一成功标记和 `finally` 执行补偿，避免多个失败分支重复恢复。暂不引入分布式事务，因为权益和业务运行在同一服务与数据库内。

### Decision: 记忆快照只读，事件由真实入口写入

首页寄语入口显式记录经过校验的打开时段；推荐和分析仅读取快照。日期统一经过安全解析，时间窗口使用包含今天的明确起止日期。

### Decision: 移除非流式请求的 THINKING 事件

同步接口只能可靠报告“文本生成开始/完成/失败”。如果以后供应商提供流式增量事件，再以独立变更恢复实时阶段。

## Risks / Trade-offs

- [菜名指纹无法识别所有同义菜] → 先使用规范化菜名满足近期去重，积累真实数据后再评估同义词表。
- [历史 AI 推荐没有曝光标识] → 新行为仅覆盖上线后的推荐，不迁移旧临时结果。
- [字符串忌口匹配可能误判复合名称] → 对明确用户限制采用偏保守策略，并通过测试覆盖常见葱、香菜、辣椒和自定义忌口。
- [应用层权益补偿仍依赖数据库可用] → 记录告警并保持恢复操作幂等，后续只有在出现跨服务结算时再引入事务消息。

## Migration Plan

1. 先部署兼容旧响应的曝光数据表与后端可选字段。
2. 部署前端对 `exposureId` 的可选支持，本地菜谱反馈保持原路径。
3. 观察 AI 推荐、反馈和权益恢复事件；异常时可回滚应用代码，新增表保留但不影响旧版本。
4. 验证后清理控制器中已被 Agent 替代的死代码。
