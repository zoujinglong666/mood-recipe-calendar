## Context

参见 [proposal.md](./proposal.md) 的动机。当前代码已具备 `UserFoodPreference`、`GuozaiMemory`、`GuozaiAgent`、异步推荐任务、曝光与交互、记录关联、推荐分享卡和时光机页面；缺口主要是内置目录只有约 117 行且内容泛化、反馈状态不完整、推荐详情没有专注做菜页、推荐记录仍强制上传照片、历史记录缺少再次做菜入口。

前端是 uni-app + Vue 3，主目标为微信小程序与 H5；后端是 Spring Boot。新实现必须复用现有登录态、请求封装、主题变量和 Wot UI，不依赖仅浏览器可用的 API。

## Goals / Non-Goals

**Goals:**

- 用现有数据表和服务完成可解释的长期记忆与最小学习闭环。
- 让干净库和旧库都安全获得 200+ 真实结构化菜谱。
- 新增单道菜、单计时器的专注做菜模式，并打通记录与时光机回流。
- 每个关键网络页面具有加载、空、失败、重试、401 恢复和深色模式。

**Non-Goals:**

- 不引入向量数据库、长期对话存储、工作流编排框架或第二套推荐引擎。
- 不做语音控制、多计时器、营养医学结论、社交 feed 或新的商业化入口。
- 不在本变更重写已有分享卡、周菜谱或 AI 图片生成系统。

## Decisions

### 1. 长期记忆继续采用“显式资料 + 即时聚合行为”

显式偏好继续保存在现有用户饮食偏好记录中；喜欢、不想吃、做过、常做菜和常见心情从现有交互、曝光与记录即时聚合，记忆接口增加统一摘要供前端展示和推荐使用。这样用户可知道数据来源，也避免保存会过时且难以删除的 AI 推断。

备选方案是加入向量记忆或 Agent 对话数据库；它会增加隐私、成本、迁移和调试负担，而当前结构化偏好足够支撑核心推荐，因此不采用。

### 2. 推荐只保留一条可解释管线

继续由现有 `GuozaiAgent` 统一处理：先应用过敏/忌口硬过滤，再排除拒绝和近期曝光，随后以喜欢、做过、菜系、标签、心情和时间习惯加权。AI 负责在合格候选中给出结果或补全理由；AI 失败直接使用同一候选集的本地最高分结果。曝光记录仍是去重和反馈关联的唯一来源。

同一推荐的反馈保存为当前有效状态或以服务端幂等规则去重，避免连续点击重复加权。“做过”按钮仅打开记录草稿，真正的 MADE 行为由记录成功统一产生。

### 3. 菜谱目录改为版本化资源并按名称幂等同步

把 200+ 菜谱放入后端资源文件，沿用项目已有 JSON 解析能力读取，不增加依赖。启动时逐条按规范化菜名查找：不存在则插入；存在且属于占位目录内容则在原主键上更新；用户数据和引用关系不删除。目录测试直接验证数量、唯一性、字段、JSON 和占位词，成为最小且可靠的发布闸门。

备选方案是清空后重种或写一次性 SQL；前者破坏外键关联，后者难以兼容不同环境和重复部署，因此不采用。

### 4. 做菜模式使用页面参数草稿和本地时间戳

推荐页与时光机先把现有 `RecipeItem` 所需字段写入一个固定键的本地做菜草稿，再打开新做菜页。页面一次只突出当前步骤，食材可折叠查看；仅提供一个计时器，以 `deadline` 而不是递减次数计算剩余时间，使切后台后仍准确。进度按菜谱标识存储，完成或明确重置后删除。

微信小程序使用可用的轻量震动；H5 捕获不支持情况并仅显示视觉反馈。此设计不要求新增后端做菜会话表，因为跨设备同步并非当前核心需求。

### 5. 记录接口使用客户端提交标识保证重试幂等

推荐/做菜草稿携带菜谱、曝光、推荐图片和一个客户端生成的提交标识。记录页有来源草稿时允许不上传照片并使用推荐图片或现有占位图；直接手动记录仍保持清楚的表单语义。服务端以当前用户和提交标识识别同一提交，记录与 MADE 行为在同一事务中完成。

保存成功后进入时光机详情；失败保留草稿。时光机已有分页与详情能力则直接扩展入口，不另建收藏或历史系统。

### 6. UI 只扩展现有锅仔设计系统

今日推荐保持菜品为主角，锅仔只承担一句个性化解释；做菜页用大字号步骤卡、明确进度和底部双操作，不叠加信息密集仪表盘。所有触控目标至少 88rpx，使用现有 CSS 变量适配深色模式，图标使用已有组件，锅仔图片使用现有静态资源。

## Risks / Trade-offs

- [按菜名同步可能遇到同名异菜] → 目录内强制名称唯一；仅更新已识别的内置占位记录，不覆盖用户创建内容。
- [行为聚合在数据量大时变慢] → 只读取近期有限窗口并复用现有查询；出现真实性能证据后再加聚合表。
- [本地做菜进度无法跨设备同步] → 当前接受单设备会话；只有用户验证需要跨设备后才增加服务端会话。
- [AI 输出仍可能不稳定] → AI 只能在通过硬约束的候选与结构校验内工作，失败回退本地目录。
- [推荐图片远程失效] → 记录显示时使用统一图片兜底；不在本变更复制远程图片到对象存储。

## Migration Plan

1. 先发布菜谱目录校验与幂等同步，验证旧库在不改主键的情况下补齐至 200+。
2. 发布反馈幂等和记录提交标识，保持旧客户端字段可选以兼容滚动升级。
3. 发布记忆摘要、推荐状态和新前端页面；旧数据通过即时聚合自然生效，无需离线回填。
4. 以空库和旧库各执行一次后端测试，再执行前端类型检查、H5 构建和微信小程序构建。
5. 回滚时可撤回新页面与接口；新增菜谱保留不会影响旧版本，新增可选字段保持向后兼容。

## Open Questions
