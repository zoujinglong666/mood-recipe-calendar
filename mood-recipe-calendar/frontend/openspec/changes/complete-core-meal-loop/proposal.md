## Why

项目已经分别具备偏好记忆、AI 推荐、反馈和记录能力，但它们还没有形成稳定的“记住我 → 推荐一餐 → 陪我做完 → 留下记录 → 下次更懂我”闭环；同时当前内置菜谱仅约 117 条且大量使用占位食材与通用步骤，无法支撑可信、低重复的长期推荐。现在应停止扩展二级功能，先把用户每天会反复使用的核心链路做完整。

## What Changes

- 将现有口味、菜系、忌口、葱/香菜、辣度和健康目标整合为可查看、可修改、可清除的“锅仔长期记忆”，并把做过记录和推荐反馈作为可解释的派生偏好，而不是保存不可见的 AI 猜测。
- 完善今日智能推荐：优先使用长期记忆、当天心情、近期曝光、喜欢/不想吃/做过反馈和历史记录；AI 不可用时仍由本地菜谱给出可解释结果。
- 让“喜欢 / 不想吃 / 做过”反馈有明确状态且真正影响后续排序；“做过”进入预填记录流程，保存成功后才完成做过闭环。
- 提供至少 200 道唯一、结构化、可执行的内置菜谱，并在空库或旧库升级时幂等补齐；禁止使用“主料/配菜”等占位食材和复制粘贴的通用步骤。
- 新增专注式做菜模式：按步骤逐屏前进、查看食材、使用本地倒计时、意外退出后恢复进度，完成后进入一键记录。
- 打通推荐、做菜、记录和菜谱时光机：推荐信息预填，照片与感想可后补；保存后能在时光机查看，并从历史记录再次打开菜谱或重新开始做。
- 继续复用现有 `GuozaiAgent`、推荐任务进度、`RecipeInteraction`、`RecipeExposure`、记录 API、分享卡与主题变量，不引入向量数据库、新 Agent 框架或新 UI 依赖。

目标是让首次安装与旧数据库升级后都能完成“选心情 → 获得不重复且有理由的菜 → 开始做 → 一键记录 → 时光机再做一次”。非目标包括社交动态、语音助手、医学营养诊断、支付和新的会员权益。

验收以以下结果为准：自动校验菜谱数不少于 200 且无占位内容；连续推荐不会立即重复已拒绝或近期曝光菜谱；三类反馈在刷新后保持一致；做菜进度可恢复；无照片也能保存由推荐产生的记录；记录可在时光机回看并再次进入做菜模式；H5 与微信小程序均覆盖加载、空数据、失败、恢复和未登录状态。

## Capabilities

### New Capabilities

- `guozai-food-memory`: 定义锅仔可解释、可编辑、可清除的长期饮食记忆及其在推荐中的使用边界。
- `personalized-daily-recommendation`: 定义基于心情、长期记忆、近期曝光与三类反馈的今日推荐和降级行为。
- `structured-recipe-catalog`: 定义 200+ 内置结构化菜谱、内容质量和幂等补齐规则。
- `guided-cooking-mode`: 定义移动端逐步做菜、计时、进度恢复及完成出口。
- `meal-record-return-loop`: 定义推荐/做菜到一键记录、时光机回看与再次做菜的回流链路。

### Modified Capabilities

无。现有变更中的健康目标、喜欢菜系、推荐进度和分享卡能力保持兼容，本变更通过新的完整能力规格将它们接入核心闭环。

## Impact

- 后端：用户饮食偏好与记忆摘要、`GuozaiAgent` 推荐排序、反馈幂等处理、菜谱种子与校验、记录关联查询。
- 前端：锅仔记忆页、今日推荐页、新增做菜模式页、记录页、时光机详情页，以及对应 API 类型和页面路由。
- 数据：旧数据不清空、不重排主键；菜谱按稳定名称幂等补齐，现有推荐曝光、交互和记录关联继续有效。
- 跨端：计时和进度恢复使用 uni-app 存储与时间戳；微信小程序保留震动和分享能力，H5 不支持的能力提供无阻断降级。
- 依赖与安全：不新增运行时依赖，不在前端或仓库写入 AI 密钥，不把用户备注正文发送到推荐提示词或运营埋点。
