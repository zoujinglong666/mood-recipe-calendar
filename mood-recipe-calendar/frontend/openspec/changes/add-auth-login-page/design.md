## Context

请求层已能识别 HTTP/业务码 401 并清除本地会话，但当前只广播事件，业务页自行承受失败。登录实现已封装在现有工具中；“我的”页有登录卡片，尚无可作为统一恢复落点的页面。

## Goals / Non-Goals

**Goals:**

- 将会话失效恢复收敛到一个独立、可深链的登录页。
- 保留安全的回跳目标并处理并发 401。
- 延续锅仔视觉与深浅色主题，适配微信小程序和 H5。

**Non-Goals:**

- 不修改服务端 Token 签发、微信 code2session 或用户资料接口。
- 不在 H5 模拟微信登录，也不新增账号密码、手机号或第三方身份体系。

## Decisions

- 在请求层的单一 401 分支完成清会话、写入一次性回跳目标并发出全局登录恢复事件，而不是在每个 API 调用页补跳转；这可覆盖上传和普通请求，并消除并发重复跳转。
- 由应用根部监听恢复事件并导航到 `/pages/login/index`；登录页不把自身或不受信任 URL 作为回跳目标，成功后仅恢复内部页面名与查询参数，默认回到“我的”。
- 登录页复用 `ensureLogin` 和既有 CSS 主题 token；微信端使用 `uni.login`，H5 仅显示降级说明，避免新增 SDK 或浏览器专属依赖。
- 使用轻量内存锁加一次性本地存储回跳信息；相比新增 Pinia 模块或后端会话字段，足以解决一次登录过程内的并发 401，且退出后不会保留陈旧跳转。

## Risks / Trade-offs

- [401 来自登录页自身] → 登录页不发起需要鉴权的初始化请求，并忽略对自身的重复跳转。
- [回跳目标不安全或失效] → 仅保存白名单内部路由信息；恢复失败时回到“我的”。
- [H5 无法完成微信授权] → 显示明确说明与返回，不让用户困在加载态。
- [登录失败] → 保留登录页和重试按钮，不恢复旧 Token。

## Migration Plan

1. 发布新登录路由与全局 401 跳转逻辑。
2. 在微信开发者工具验证业务码 401、HTTP 401、重复 401、登录成功回跳与 H5 降级。
3. 需要回滚时移除全局事件监听，恢复原“我的”页登录卡片入口；后端接口无需迁移。
